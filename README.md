# PDF preview memory: bench results

Date: 2026-10-11. Image: public `docuseal/docuseal:3.3.1` (`linux/amd64`). DocuSeal `master` at the time is
`c6a7555` (= tag `3.3.1`); `lib/templates/process_document.rb` has the same SHA-256 in the repo and in the
image (`413e21fc…`). Harness and raw data: `bench/` (`bench/results/<run>/`).

## Recommendation

Variant B (one page at a time, no thread pool), which is `process_document.patch`.

- It is the only variant that survives the whole scenario at 740 MB: 4 out of 4 runs, 7/7 uploads,
  `memory.peak` 482-485 MB, max anon 445-449 MB (about 255 MB of headroom).
- Stock is OOM-killed on the 2nd upload in 4 out of 4 runs. C (pool of 2, pages rendered in slices of 2)
  passes the 5 uploads in a row but is OOM-killed when 2 uploads run at once, in 4 out of 4 runs.
- Previews are byte-identical in every run of every variant (same 16 checksums, same order).
- Speed: on 1 CPU, B is as fast as stock (3.3-3.4 s per document vs 3.4-3.9 s for stock given 2 GB). On
  2 CPUs, one upload alone is slower than stock (3.0-3.3 s vs 2.3-2.5 s, about +35%), and two uploads at
  once take the same time (3.6-3.7 s vs 3.6-4.0 s).
- C does beat B on 2 CPUs (2.4-2.6 s per document), but only by running 2 PNG encodes at once, and each
  encode needs about 60 MB of transient memory (see "Why the pool costs memory"). It cannot keep the speed
  without losing the memory bound, so B is the recommendation.

## Scenario and method

- Container: `--memory=740m --memory-swap=740m` (no swap), `--cpuset-cpus=0` ("1cpu") or `0,1` ("2cpu");
  reference runs at `--memory=2g` ("2g") to see stock's full-scenario peak and speed. `--restart=no`.
- The image runs as shipped: Puma with the embedded Sidekiq and embedded redis-server (same cgroup), SQLite
  in `/data/docuseal`, Active Storage on local disk. No Postgres, no external Redis.
- How previews are triggered in the open-source edition: the web upload form, `POST /templates_upload`
  (`TemplatesUploadsController#create` → `Templates::CreateAttachments.call` → `handle_pdf_or_image` →
  `Templates::ProcessDocument.call` → `generate_pdf_preview_images` → `generate_document_preview_images`).
  It runs **inline in the Puma request thread**, not in a Sidekiq job; the OSS API has no template creation
  endpoint (`api/templates` is `update show index destroy` only). The bench drives this exact HTTP request
  with curl and a session created through `/setup`; the request duration is the preview duration
  (`app.log` shows `TemplatesUploadsController#create` at 4319 ms for the first stock upload).
- Two uploads at once are therefore two Puma threads rendering 16 pages each in one process.
- Test PDF: `bench/test-22-pages.pdf`, generated by `bench/make-test-pdf.rb` (deterministic, no
  dependencies, MD5 `d8b69dae15942a95abba5b0e15a9ba0a`), 22 A4 text pages → 16 previews (pages 0..15),
  each rendered at 1400 × 1980 (11.1 MB RGBA bitmap).
- Per run: 20 s rest, 5 uploads one after another 5 s apart, then 2 uploads at once, then 10 s rest.
- Memory: a privileged sidecar reads `/sys/fs/cgroup/docker/<id>/` every 0.25 s from outside the
  container: `memory.current`, `memory.peak`, `anon`/`file` from `memory.stat`, `oom_kill` from
  `memory.events`. "Rest anon" is the median anon over the 5 s before the first upload. On killed runs
  `memory.peak` reads ~740 MB because it saturates at the limit; max anon is the last sample before the kill.
- OOM: `docker inspect` `.State.OOMKilled` (true and exit code 137 on every killed run).
- Previews: after the run the data directory is copied out; every `preview_images` blob is listed with its
  `active_storage_blobs.checksum` (base64 MD5) and checked against the MD5 of the file on disk
  (0 mismatches in all 22 runs); the copy is deleted afterwards since it holds generated secrets. A document's signature is the MD5 of its 16 `filename:checksum` pairs.
- Host: Apple silicon Mac, Docker Desktop 29.8.1 (VM with 14 CPUs, 7.7 GB), `linux/amd64` under Rosetta
  (`/proc/cpuinfo`: VirtualApple). The first upload of each run includes warm-up, so it is the slowest.

## Variants

- A `bench/variants/stock.rb`: `master`.
- B `bench/variants/sequential.rb`: render a page, copy it into vips, `bytes.clear`, encode and upload it,
  close the page, next page; attach the blobs in page order afterwards. Identical to the patched file.
- C `bench/variants/bounded.rb`: keeps `FixedThreadPool(CONCURRENCY = 2)`; renders pages on the calling
  thread in `each_slice(concurrency)`, `bytes.clear` after the vips copy, waits for each slice
  (`Promise.zip(...).value!`) before rendering the next. pdfium handles stay on the calling thread, as in
  stock.

## Why the pool costs memory

`bench/probe-encode.rb` (one process, 1 CPU, libvips cache off, `GC.start` between pages):

- pdfium render + vips copy: ~20 ms per page (297 ms for 16 pages).
- `build_and_upload_blob` encode (sRGB copy, `stats`, palette PNG): ~155 ms per page (2.5 s for 16 pages).
- RSS 94 MB before the first encode, high-water mark 156 MB after it: one palette PNG encode of a
  1400 × 1980 page needs ~60 MB of transient memory (libimagequant works on a full float copy of the image).

`vips_cache_operation_build` is attached with `blocking: true` in ruby-vips 2.3.0, so encodes on pool
threads really run in parallel. Memory therefore grows with the number of concurrent encodes, about
60 MB each, on top of the pages held:

- Stock: 16 pages × (11 MB bitmap String + 11 MB vips copy) held by the promise closures until
  `Promise.zip(...).value!` returns, plus 2 encodes: ~350 + ~120 MB ≈ the +475 MB measured.
- C: 2 pages + 2 encodes per request; two uploads at once means 4 concurrent encodes → OOM.
- B: 1 page + 1 encode per request; two uploads at once means 2 encodes.

Rendering is only ~10% of the work, so overlapping it with a single encode thread would not help speed.

## Limits and what was not verified

- RSpec not run (the suite needs Postgres, Chrome/cuprite). No spec asserts preview count or order
  directly; `generate_document_preview_images` is covered only indirectly through
  `spec/factories/templates.rb` (calls `Templates::ProcessDocument.call`) and `spec/system/templates_upload_spec.rb`.
  The bench's checksum comparison covers output identity for a 16-page text PDF; form PDFs (`doc.form?`,
  `flatten`) were not exercised.
- RuboCop 1.86.0 (with rubocop-performance 1.26.1, rubocop-rails 2.34.3, rubocop-rspec 3.9.0, the repo's
  `.rubocop.yml`) on `ruby:4.0.5`: no offenses on the patched file.
- amd64 under Rosetta only; no native arm64 run. Absolute timings under Rosetta are slower than native; the
  memory numbers are what matter.
- Only the generated 22-page text PDF was run; other real-world PDFs (scans, mixed page sizes) were not.
- 2 repetitions per variant and CPU setting (4 per variant at 740 MB); timings vary by ~0.3 s between runs.
- Possible follow-up, not in this PR: a process-wide encode pool or semaphore shared by all requests would
  bound concurrent encodes per process and could keep C's single-upload speed; it adds shared state and
  cross-request queueing, so it is a separate design discussion.
